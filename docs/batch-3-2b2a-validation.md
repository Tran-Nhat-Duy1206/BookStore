## Implemented boundary

- [Server-only factory](../src/server/security/provider-proof.ts) uses the canonical provider client and the accepted auth/staff purpose profiles only. No experimental imports, environment fallback, permissive signup switch, caller-injected provider/hooks or generic exported SDK handler. Its logical `.invalid` origin exists only in in-memory SDK requests; no authentication network listener.
- Real SDK signed-cookie/session resolution plus an independent auth SQL check of committed current session ID/user/token/expiry. Result is a five-field provider-authenticated DTO or static unauthenticated/unavailable state, never a provider record/token. This is a point-in-time authentication observation, not permission or MFA admission.
- Purpose-role attributes and database/schema privileges are checked before operations, including **any column-level SELECT** on private token/password/factor tables. Missing schema USAGE is not bypassed by granting it: metadata checks use catalog OIDs. Staff cannot read credentials; auth cannot write admissions/grants/audit or DDL.
- The kernel's default trusted resolver remains null. The new resolver is NOT installed into any application caller. Password success, provider authentication, stored factors and enrollment flags do not establish staff admission.
- Private factory-owned WeakMaps correlate real maintained password/TOTP operations and reject copied/forged/cross-factory references. Their objects are investigation metadata, not bearer credentials, alternate sessions, signed receipts or durable one-use proofs. The provider cookie and database session remain the only authentication mechanism.
- [Pure proposed-binding comparison](../src/server/security/provider-proof-contract.ts) validates safe metadata and reports mismatches; **every outcome has `admissionAllowed:false`**. A structurally identical serialized copy can compare as metadata but is not authenticated evidence; the factory provenance gate rejects it.

## What the proposed proof contract still does NOT guarantee

The observation binds actual SDK operation, user/final session, purpose, interval, original/current authorization versions and transient factor identity/change metadata. It is intentionally **non-authorizing**. In particular, matching metadata does not prove that no relevant ledger event is pending or that governance/permissions remain valid.

B.2b would need separately approved positive authority and private challenge, issuer/audience/jti/expiry, canonical authenticated receipt or reviewed narrow attestor credential, durable one-use challenge/proof/OTP consumption, credential/factor epochs, immutable original login lineage/deadline and independent revocation tombstones. Finalization must recheck live state after governance locking under READ COMMITTED and consume proof+admission+success audit atomically. Do not transplant the experiment's broad writer, grant staff raw INSERT, rebase old evidence after reconciliation, revive a revoked session or turn enrollment/recovery into normal admission.

SDK valid OTP is therefore usable as an observed event in a private successful operation, but **the SDK supplies no complete signed/durable positive-admission proof**. B.2a does not invent one. Operational admission is NO-GO without further approval/design/validation.
