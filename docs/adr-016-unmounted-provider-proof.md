## 1. Decision and hard boundary

Implement only an **unmounted, server-only, dev/test-only canonical provider integration**: Better Auth1.7.18 plus Prisma adapter1.7.18, purpose clients, authoritative SDK session resolution and investigation of actual SDK TOTP completion, commit and effective-cookie behavior. The [server-only factory](../src/server/security/provider-proof.ts), [pure binding contract](../src/server/security/provider-proof-contract.ts), [canonical investigation suite](../tests/provider-proof/provider-proof.test.ts) and [isolated configuration](../vitest.provider-proof.config.ts) implement this scope. They use existing canonical models and purpose roles, not an operational credential rollout.

Use canonical provider models and the existing single SQL migration history. Do not import experimental provider/schema/client/admission modules. Preserve all exact dependency pins and dev-only classification; this unmounted slice does not require runtime promotion. Preserve all five existing CI jobs (frontend, PostgreSQL catalog, isolated Better Auth spike, unfiltered full dependency audit, B.1 foundation); only an isolated sixth unmounted provider-proof job is appended. A job definition is not a successful run.

The kernel's [default trusted resolver](../src/server/security/kernel.ts#L88-L91) remains `async () => null`. No application caller, route, Action, RSC, frontend import or UI is wired to this integration. Never accept caller-controlled provider instances, session-reference claims or resolver authority. No live admission writer, signing/MAC receipt, durable proof consumer, replay database/state, migration, operational bootstrap, real identity/account, invitation/recovery, staff/business CRUD, customer/commerce, deployment or paid service is authorized.

## 4. Proposed B.2a observation — deliberately not proof authority

The implementation produces **only a non-authorizing in-process observation of the actual maintained SDK operation**, not an attestation that a request is permitted. The factory privately owns the provider and operation path. No injectable verifier callback, arbitrary claims constructor, public branding function or caller-selected provider can manufacture a positive observation.

Proposed observation data is a strict, immutable safe-ID envelope: server operation ID and fixed purpose; SDK-resolved user and initial/final session IDs where available; expected authorization version **before and after**; factor-ID lineage before/after; operation start/end timestamp interval. IDs must be validated bounded opaque references, not emails, tokens, challenges, OTPs or credential material. The interval is a bounded observation interval, not an invented exact MFA/commit instant. Do not serialize raw SDK responses, secrets, factor data, cookie values, passwords or codes.

Record observations only inside the private real-SDK success path and retain object identity in a private `WeakMap`. Copying, spreading, JSON roundtripping, casting, fabricating a structurally identical object or passing an observation from another factory must not confer provenance. A TypeScript brand alone is insufficient. The WeakMap is a local provenance and transient change-detection aid only: no cryptographic authenticity, process isolation, durability, exactly-once semantics or replay guarantee follows from it. Process loss discards observations; there is no restore or consumption API.

The factory's private provenance gate precedes a pure comparison of original bindings, version equality, factor identities, same user/final authoritative session, fixed purpose and coherent start/end interval. The pure function alone does NOT authenticate provenance: a serialized metadata copy can match shape/bindings while remaining entirely non-authorizing. A private transient fingerprint detects credential/encrypted-factor changes but is not a durable credential/factor epoch. It must **always return `admissionAllowed: false`**, including on valid bindings. Use a separate binding-valid result/reason, never a positive authorization result. **Valid binding is not MFA-proof attestation**, nor evidence of an application-approved primary ceremony, durable replay reservation, current admission or operational MFA completion. Pending/changed/unavailable state must remain non-authorizing, not silently adopt the latest version.

No signature, signer/verifier key, proof jti/challenge persistence, database finalizer, admission insert/update, replay reservation or durable consumer is created in B.2a. The receipt/attestor alternatives in the full plan remain proposals requiring explicit B.2b authority review.

## 5. Session, purpose-client and completion investigation contract

- Factory is explicit, lazy and server-only: no import-time connection, implicit environment fallback, generated startup secret or permissive runtime instance. Public fixture builds remain auth-config-free. Invalid explicit configuration fails closed with generic safe errors.
- Auth-purpose client alone performs canonical provider operations, including session lookup cleanup if the pinned SDK does so. Staff and worker use only their existing reviewed purpose capabilities. Validate exact owned URL/profile plus actual connection role attributes/no memberships; no catalog-reader or migration/bootstrap fallback, shared broad client or new credential purpose.
- Use existing owned disposable55436local/55437CI boundaries and synthetic `example.invalid` fixtures only. Preserve catalog and experimental guards unchanged, no5432/other-project services, no force cleanup, no new operational namespace. Provisioning of synthetic test fixtures is not an operational bootstrap/account tool.
- Resolver uses actual SDK session lookup, not cookie presence or caller-provided IDs. Disable session refresh/cache and project only safe user/session references. Anonymous and persistence/configuration failure must not be conflated to hide faults; safe failure remains denied. No kernel/app composition is installed.
- Investigate actual password->challenge->TOTP, active-session TOTP and synthetic enrollment rotation separately. Privately track effective validated response cookie changes, including deletion/rotation and multiple headers, then resolve the final authoritative session. Never treat the old JSON bearer token, HTTP200, `twoFactorEnabled`, `verified`, generic hook or created-session event as sufficient evidence.
- Investigate failure after challenge consumption, session creation, cookie construction and factor mutation; read authoritative post-operation state and relevant ledger effects. Provider completion does not imply local/staff atomicity or browser cookie delivery. Ambiguous completion must not be labeled certain rollback.
- Do not hold staff/governance locks while awaiting the separate provider connection. B.1 reconciliation retains its gate/audit/version semantics. After an invalidating factor/enrollment event, preserve the original version mismatch; do not rebase the observation. A future positive protocol needs a NEW prepared challenge/fresh verification after reconciliation, not promotion of B.2a observations.

## 6. Executed investigation and unresolved acceptance

[Validation](./batch-3-2b2a-validation.md) records56real SDK/PostgreSQL investigation cases and60pure contract cases, separate from preserved catalog/spike/foundation/storefront gates. Tests corroborate original-version and factory provenance binding, wrong/expired/replayed-code behavior, final-cookie/old-JSON-token divergence, multi-transaction enrollment, early/late persistence faults, column-level privilege drift and the closed default kernel. Pure metadata matching NEVER permits admission.

Real late enrollment failure can leave the old session deleted, a new session committed without a delivered cookie, User enabled and factor unverified. No automatic repair, broad reset or success proof is invented. Real independent challenges and active sessions can accept the same time-step OTP. These remain explicit operational blockers requiring later persistence/recovery design.

The SDK error handler is configured to rethrow into the private sanitizer: Better Call's raw console fallback is not prevented merely by disabling the SDK logger. Actual SQL-fault tests assert generic503, no observation and zero raw console errors. Purpose checks include `has_any_column_privilege` on private tables: table-level ACL checks alone missed column grants; independent review found and regression tests resolved that gap.

Final-HEAD CI is required after push, separately recorded by the Draft PR checks/comment and final report. Do not reuse old spike totals or guessed results as B.2a evidence. This ADR grants no owner acceptance, merge, B.2b, real-account or operational permission.

## 7. STOP / GO meaning

**STOP / NO-GO if a safe actual-SDK success/event boundary, completed operation, effective cookie/final-session binding or non-forgeable private observation path is not proven.** Do not patch the gap with enrolled flags, response success, invented atomicity, caller authority or a permissive admission writer. Report the limitation for owner review.

A future **B.2a GO means only that the reviewed unmounted non-authorizing contract investigation passed its actual gates**. It requires actual exact-HEAD evidence and owner review; it does not activate authentication. **Operational proof remains NO-GO until separately approved B.2b** establishes protected durable authority, consumption, version/epoch/revocation binding, cross-purpose replay prevention, atomic local admission/audit and adversarial crash/race validation. B.2c–e transport/Next/browser acceptance and B.3 ceremonies remain separately unapproved. Candidate8h/30m/5m settings are fixtures, not approved runtime policy. Website Vietnamese UI remains untouched.
