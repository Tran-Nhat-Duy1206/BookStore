## 3. Exact offline trust model

### 3.1 Independent approval root

The subject is the independently verified intended initial Owner, NOT the GitHub user/commit author/first registrant/provider emailVerified bit. D01/D02 must define verification channel, proof sufficiency, authorized approving operators/quorum, revocation and redacted evidence custody. No identities, names, emails, keys or proof records are invented here. Synthetic design contracts may be approved without collecting real identity; that cannot satisfy real activation.

A proposed protected **case envelope** has immutable server-generated case/operation identity, realm, action exactly `initial_owner_bootstrap`, identity normalization contract +intended identity reference, role exactly Owner, expected uninitialized governance revision, target source-claim binding (atomically at first authorized User INSERT and committed with its source transaction, then independently confirmed after full native completion), policy revision, approval/evidence references, absolute approved expiry. Mutable fields are only monotone case revision/state, candidate revision/source root, one-use operation ownership, terminal outcome and consumption. No caller timestamp/role/verified boolean or arbitrary subject scope. New unique constraints enforce one initial case per realm and no second activation; identifiers/history are not reusable after deletion.

There are TWO independent approvals, not an overloaded MFA flag: (i) permission to begin the exact case/identity/action, before account work; (ii) independent approval of the exact completed candidate ProviderSnapshot +candidate revision/source root +intended local principal/Owner transition and expected target versions. A DB connection authenticates its trusted service root, not the truth of external identity evidence. Evidence references are not self-verifying signatures or approval by mere possession.

Normal MFA remains the canonical private maintained SDK→VERIFIER→STAFF protocol. Offline approval can approve an initial credential/factor generation, NEVER assert that TOTP ran or create normal admission. Setup completion must separately come from the real private SDK call and exact durable source bindings. Even completed activation returns no admin session; fresh password+TOTP is mandatory.

### 3.3 Setup recording authority — separate STOP decision

Logical SETUP_EXECUTOR means the trusted private caller that actually runs maintained setup and records its setup-only outcome. It is not a browser, operator-submitted success or ordinary permission. Two mappings require owner review:

- **S1 preferred for review:** extend the ONE canonical private SDK/VERIFIER composition with fixed setup-only entrypoints. Ordinary login/step-up behavior remains unchanged; no second ordinary issuer. Additional EXEC/profile allowance still changes B.2's exact seven-function contract. NOT approved by this ADR or current task.
- **S2 alternative:** separate offline setup-only recorder credential, barred from ordinary issuer functions. This adds a NEW trusted positive SETUP recorder root, not harmless metadata merely because no ordinary admission is returned. Requires separate trust/custody review; not default or automatic fallback.

S1 cannot claim SQL credential isolation between setup and ordinary issuance: the same VERIFIER already retains normal issue EXECUTE. Only the fixed private call paths and incompatible protected case/attempt state separate those purposes; compromise of that root remains able to forge ordinary evidence, as accepted in B.2. S2 can enforce disjoint EXECUTE but adds another positive setup root. This distinction must be explicitly approved, not hidden by a logical SETUP_EXECUTOR label.

All current grants remain as-is. Function manifest below names logical future callers, NOT installed grants. If neither mapping can preserve the required authority boundary without a broader trust model, STOP for owner review. SQL cannot independently prove SDK execution; the selected private recorder is explicitly trusted, as the existing normal issuer is. A caller callback/brand/flags cannot replace it.

## 4. T1 — Pending enrollment and global replay contract (proposed)

### 4.1 Fixed private sequence

Authorized begin→one-use account-create reservation→maintained new account creation (no adoption of existing identity)→fresh maintained password sign-in/proof→fixed enable operation with password reproof→exact pending factor→pre-SDK TOTP reservation→maintained verifyTOTP→await full operation→validated FINAL effective cookie→maintained session resolution/cache off +independent committed user/SID/token/expiry lookup→setup outcome capture. No network listener, public route, exported generic provider instance/handler or permissive catch-all. No raw experimental factory promotion.

Account creation, password proof, enable and confirmation are distinct irreversible SDK boundaries. Existing signup is disabled; private signup adapter/config and API selection need owner review. Signup does not independently verify identity/email. The mapping of approved independent identity evidence to the provider emailVerified state requires a specifically reviewed maintained API or fixed offline authority operation; no automatic true flag or email service is selected. Secret URI/backups delivery stays OFF until D06/D08/D10 approve an isolated one-time channel; no argv/stdout/log/URL/analytics/artifact exposure is authorized.

Every password-bearing operation is charged through the SAME password account domain using case-bound normalized identity, fixed conservative `unknown` IP scope and15m window, including enable password reproof. MFA uses the bound provider user ID after successful new creation. No browser/header IP authority. Native SDK limiter remains enabled; its login-only challenge counters are not enrollment assurance.

### 4.2 Exact reservation invariants

Before ANY native TOTP comparison: governance-first READ COMMITTED transaction; committed before SDK; verify case/expected revision, pending subject/factor, original primary cookie/SID lineage, approved identity action, current candidate revision/root and expiry. Account and fixed unknown-IP budget keys sorted BEFORE locking/CAS of setup operation and replay row, matching existing ordering. No staff locks during SDK.

Retain EXACT current SQL derivation: domain `user-code`, payload PostgreSQL canonical `jsonb_build_array(bound_user_id, raw_code)::text`, outer framing `jsonb_build_array('BookStore.B2b.v1',domain,payload)::text` UTF8, existing HMAC-SHA256 key/realm/checksum, SAME protected replay_burns unique key/store. Code is exactly six ASCII digits, leading zeros retained. NO case/purpose/session/generation/factor/time bucket in replay identity. No new key, parallel enrollment burn table, normalization, reset or refund. Internal raw code/bind values are never logged/exposed; no generic MAC oracle.

Same current limits: password5/account/15m, MFA10/account/15m, common scope20 per password/MFA KIND/15m; budget capacity20000, replay10000, setup operation admission must not evade the current10000-attempt safety ceiling (new shared/aggregate accounting requires review). Native3/10s remains where the SDK applies it.120s primary origin captured before password verification;30s inflight deadline is the EARLIER of original primary deadline and reservation+30s;180s burn expiry is EXACTLY stored `reserved_at +180s`, where reserved_at is the trusted reservation statement's post-governance time n, NOT a later physical COMMIT/SDK/capture time. The30s inflight bound likewise uses that n. The reservation/burn MUST commit before SDK; slow commit does not extend either deadline. Case/approval TTL must also bound, never extend, these limits. Any change requires separate approval.

**Conservative H1 no-extension proposal (UNAPPROVED):** setup confirmation, durable outcome, independent final approval and activation consume within that same hard verification deadline, not after an unbounded offline human delay. Source inspection cannot establish reasonable human completion or uptime within30s. Independent identity/action authorization BEFORE setup is not independent approval of future completed credential bytes/q/root. [H1/H2 analysis and owner matrix](./b3a-critical-blocker-resolution.md) distinguishes H1 from a fundamentally NEW delayed setup-completion-fact state/expiry contract, not a longer live MFA reservation. That H2 alternative and automated predicate approval remain unselected; this paragraph does not ratify either. Operator preparation/identity proof occurs earlier; if final approval cannot be performed in time, deny and leave the case nonauthorizing. No grace window/repeated code or hidden deadline renewal. Whether an alternative long-lived SETUP outcome can safely serve later generation approval is NOT selected; that would be a different contract requiring owner review. New TTLs/policy are unset, not silently defaulted.

Live replay conflict denies; original burn/charge remains on invalid code, SDK error, timeout, lost response, crash or audit failure after earlier commit. No lease reassignment/inflight takeover or automatic SDK retry. Old normal login/step-up reservations are unchanged; future replacement must use this exact global domain too, but B.3d is not implemented or authorized.

### 4.3 Candidate history and permitted transition grammar — unresolved mechanism

Before first pin, equal hashes do NOT defeat A→B→A. Require NEW protected per-subject/case monotone candidate revision +bounded source journal/root in the SAME provider transaction, retaining opaque row identity, fixed mutation/field mask and keyed before/after projections, never raw credential/factor data. Track BOTH OLD/NEW affected subjects and either OLD/NEW credential membership, cascades/bulk/deletes/reinserts and aborted-versus-committed changes accurately. Tracking must cover a native NEW subject from its FIRST User INSERT INCLUDING the authenticated same-source-transaction subject claim, before any post-call private completion confirmation; that confirmation cannot initialize history to a convenient latest root or hide earlier source changes. The causal binding of that unbound creation operation is part of B03, not solved by matching email. History cannot cascade with provider deletion or be reset by workers.

Expected confirmation changes still ADVANCE this revision. The fixed grammar may permit ONLY the captured factor's verified false→true with same ID/user/secret/backup bytes, User twoFactorEnabled false→true with identity/email/emailVerified unchanged, plus the expected separate session creation/old deletion. ProviderSnapshot excludes sessions; session history/binding is checked separately. Native failure counters outside the accepted snapshot do not silently become generation changes. Enable/re-enable that replaces pending secret/backups is a NEW source generation; never automatically regenerate/adopt it.

A PRECOMMITTED one-use setup reservation must authorize the exact source transition grammar/previous revision/root/deadline and be causally correlated with the provider writes across the SDK's separate commits. A journal recording what happened is necessary but not proof the SDK caused it. Neither caller-set GUC nor event-kind/count/post-hoc success flag is sufficient. Private actual maintained completion is additionally mandatory. Unexpected critical write/interleaving/extra factor/ABA invalidates old operation/outcome/approval even if final bytes match; never refresh their root to latest.

**OPEN BLOCKER B03:** stock hooks/transaction configuration does NOT supply exact authenticated same-source-transaction reservation consumption. Follow-up source inspection establishes public custom-adapter construction surfaces and fixed-login/client composition as candidates, not end-to-end proof. The preferred C3 candidate would precommit an immutable LOGIN→case/op mapping, atomically claim the NEW subject on its first actual User INSERT, and record source history/cursor under that authenticated LOGIN in every native transaction. This adds trusted writer root L and new SQL/ACL/lifecycle/read-scope contracts; SQL attribution is not native SDK proof. C2's authenticated permit/transaction-ledger wrapper would also change the persistence contract and has unresolved full-coverage/rollback/unknown permit lifecycle. See [critical investigation](./b3a-critical-blocker-resolution.md). Exact registry/journal/grammar/fences and actual SDK/PG proof have NOT been established or approved. A new write capability/correlation mechanism may alter the B.2 trust/ACL contract. Do not present this grammar as an installed enforcement mechanism or call T1 implementation-ready. No SDK monkeypatch, broad update hook, injected verifier, trigger bypass or new generic writer is authorized to solve it. Owner must review a concrete binding design before code.

### 4.4 Final outcome is setup-only

After actual native success, await rotation/final factor commit, validate all cookie updates and resolve actual committed SID/token/user/expiry. Native JSON may carry old token. Wrong/missing final jar, deleted/retired SID, incomplete operation, unexpected candidate revision, expired burn/deadline, missing/BLOCKED source evidence or required audit denies. Existing source events are reconciled deny-only OUTSIDE held locks; expected mutation is not permission to mark them processed or suppress retirement. Then recheck journal/root and separately captured target versions, never old MFA-version rebase.

Outcome reference is private one-use setup state, not ordinary `issue_evidence`, admission, session control or recent MFA. No normal finalizer accepts it. Store no replayable bearer response; setup sessions are deny-only retired/tombstoned before activation, SDK deletion separately outside locks if required. Later normal login uses a new password origin/challenge/SID and fresh TOTP; an over-bound clock sample or replay collision still denies.

## 5. T2 — Generation-approved Owner predicate and SQL-side contract

Let S(u) mean EXACT005 structural eligibility. Define proposed E(u): S(u), no retired-user tombstone, and at least one NONRETIRED approved generation owned by u whose fingerprint equals current ProviderSnapshot(u). Count DISTINCT subjects, not joined factors/pins. When governance active require count(S)≥1 AND count(E)≥1. No active session/admission/attempt/recent-MFA, backlog or instantaneous-login requirement inside E. Pending/BLOCKED/clock/session/versions remain separate normal guards and activation prerequisites. Do NOT reuse live_generation: it requires active governance and unrelated liveness, causing bootstrap circularity. MAC/key/evaluation failure denies, never maps unknown to eligible.

Proposed additive contract (001–007 stay immutable):

- Retain all existing governance BEFORE STATEMENT locks and structural assertions. ADD corresponding governance BEFORE STATEMENT locking on approved_generations and retired_users as well (they have no such current005 triggers), not only caller-side lock conventions. Add generation-aware AFTER STATEMENT checks for User/Account/TwoFactor, principals/role_grants, approved_generations and retired_users; retain existing Session/admission checks. Cover every private direct retire_subject path, not just SDK statements. No temporarily disabled constraint or deferred window permitting zero E-owner commits.
- Provider row-level control_generation retirement happens BEFORE provider AFTER STATEMENT assertion. The new assertion must see source update AND nested pin retirement in the SAME source transaction. On sole E-owner nonempty password/secret/backups/email mutation, pin retirement makes E=0, so raise and rollback that entire source transaction. No worker delay or manual repair gap. With another E-owner mutation may commit, but old pin stays retired after restoring bytes.
- Source retirement +candidate invalidation must consider OLD and NEW subjects/provider membership. Current immutable-binding triggers reject rebinding; do not rely solely on006's NEW-side account classification for a general future history detector. Runtime TRUNCATE/trigger disable/DDL/ownership/role membership/replication-role bypass remain denied by ACL/profile checks; DML triggers alone do not cover TRUNCATE or an offline owner adversary.
- Generation ID/subject/fingerprint/approval identity are immutable; retired false→true only, no delete/reinsert ID or unretire. Retired-user and spent case/approval history survive provider/session deletion. New helper must have fresh READ COMMITTED post-wait/post-statement visibility (VOLATILE/default volatility as appropriate), not blindly copy STABLE; actual PG trigger/cascade/snapshot proof is mandatory later.
- Bootstrap→active requires exactly ONE S and ONE E, both same immutable case subject and NEW exact case-approved pin; approved local transition/version and case consumption/audit atomic. No active-governance prerequisite in the eligibility component; no session needed. No active→bootstrap/uninitialized/recovery_locked, unlock/reset or universal zero-Owner exception added by B.3a.

**Migration compatibility BLOCKER B05:** accepted B.2 can contain active structural Owner with no approved generation. A future additive invariant must preflight and STOP/keep auth OFF for owner-reviewed disposition, not grandfather/autoapprove or silently install a weakened predicate. Newly owned synthetic fixtures may later be adapted under explicit offline fixture authority, labelled nonceremony, while preserving existing assertions. No operational repair/reset is proposed. Baseline availability limitation is not retrospectively relabelled an exploited bypass.

T2 is a proposed stronger security/availability semantic, requiring D05 and SQL/ACL/trigger review; not approved merely because safer on paper. Structural/generation eligibility still cannot guarantee password knowledge, decryptability, good clocks, reachable provider/audit or arbitrary-load uptime. Conservatively reject sole-Owner destructive mutations until separately approved recovery exists; no automatic reapproval or recovery bypass.
