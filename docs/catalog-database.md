# Batch 3.1 — Local catalog database and read foundation

## Scope and source

This batch adds local PostgreSQL persistence for catalog metadata only. [ADR-010](./adr-010-catalog-persistence.md) resolves the approved relationships; [Phase 3 plan](./phase3-plan.md) keeps later batches explicitly unapproved.

- DATA_SOURCE defaults to `fixture`; only exact `fixture` or `database` values are accepted. Explicit empty/invalid values fail.
- Fixture mode requires no database URL, running database or cloud service.
- Database mode is explicit local/CI opt-in and never substitutes fictional fixtures when a query fails.
- The server-only facade projects normalized records into the existing Book/Series/Category DTOs. It does not send Prisma records or database UUID graphs to client components.
- Only complete, published, demo-marked records are eligible for this legacy demo UI. Real-content publishing is not approved by this batch. Unknown year, unsupported prepacked presentation and incomplete relations are not invented into legacy book DTOs.
- Editorial/release content remains fixture-backed; there are no CMS, auth, admin, inventory or commerce operations.

## Toolchain and isolation

Node24.19.0, pnpm11.7.0, Prisma/client/adapter-pg7.10.1 and pg8.23.1 are pinned. Prisma's registry CLI latest tag pointed to an RC during setup; this batch deliberately selects stable7.10.1. The generated client is ignored and regenerated by typecheck/build.

Prisma requires engine/esbuild lifecycle scripts. The workspace build allowlist names only `@prisma/engines`, `esbuild` and `prisma`; it does not allow arbitrary dependency scripts globally.

Use PostgreSQL18. Docker Compose supplies `postgres:18.3-alpine`, a dedicated named project/volume and loopback port55432. On the implementation host Docker was unavailable, so the existing PostgreSQL18 **executables only** initialized a brand-new cluster under this project's ignored local directory. Existing PostgreSQL services/data directories and port5432 were not reused or changed.

Database URL guards require:

- `postgres`/`postgresql`, loopback host, explicit port55432 or55433.
- User `bookstore_catalog`, a nonempty local-only password and an approved `bookstore_catalog_*` development/test database name.
- No arbitrary URL query parameters, external hosts, default5432/5433, unrelated usernames/databases or embedded whitespace.
- Normal production-mode database reads are rejected. `BOOKSTORE_LOCAL_DB_READS=1` permits only a deliberate local production-build smoke test; URL restrictions still apply.

The guard is also applied by Prisma configuration, migration wrappers, seed/client factories and integration helpers. It is not a production infrastructure/security policy; deployment remains forbidden.

## Default fixture development

From the workspace root:

```sh
pnpm install --frozen-lockfile
pnpm dev
```

No environment file is required. Build/typecheck regenerate Prisma without connecting to PostgreSQL. The generation-only fallback URL points to non-listening port1 and is never used by runtime database reads or authorized write scripts.

```sh
pnpm typecheck
pnpm lint
pnpm test
pnpm build
pnpm exec playwright install --only-shell chromium
pnpm test:e2e
```

## Native local PostgreSQL setup

Choose native **or** Docker, never both on the same port. Check55432/55433 availability first; do not stop another project's service to make space.

```sh
pnpm db:local:init
pnpm db:local:start
pnpm db:migrate
pnpm db:seed
pnpm db:seed
pnpm test:db
pnpm db:local:stop
```

The native helper uses installed PostgreSQL18 binaries, not Windows services. `PG_BIN` can be set in the invoking process to the correct bin directory when it is not the default Windows path. Initialization refuses an existing unmarked data directory or an existing environment file rather than overwriting it.

Initialization generates random local-only credentials in ignored local state and a new ignored environment file with fixture mode. Do not print, commit or upload these files. POSIX file mode0600 is requested where supported; Windows access follows the existing directory ACLs, which this batch does not change.

Start refuses an occupied port. Stop/status are scoped to the exact project-root/data-directory/port ownership marker. There is no service-wide stop, force-kill-by-port, shared reset or deletion command. Stopping leaves the owned development data available for the next start.

## Docker alternative

Docker was not available on the implementation host; the supplied Compose configuration is the alternative local runtime. CI independently exercises its pinned PostgreSQL image.

Prepare an ignored environment file from the documented example, with a newly generated local-only password, matching DATABASE_URL and TEST_DATABASE_URL. Then:

```sh
docker compose --env-file .env.local up -d catalog-db
pnpm db:migrate
pnpm db:seed
```

Compose creates the development database only. For integration tests, create a separate empty `bookstore_catalog_test` database **inside this newly created BookStore container**, owned by `bookstore_catalog`, and point TEST_DATABASE_URL there. Never use an existing project database as the test base.

Stop only this named Compose project/service when finished. Do not delete its data volume as routine cleanup.

## Explicit local database-mode storefront

After applying migrations and seeding, set these values in the invoking process or ignored local configuration:

```dotenv
DATA_SOURCE=database
DATABASE_URL=postgresql://bookstore_catalog:LOCAL_ONLY_PASSWORD@127.0.0.1:55432/bookstore_catalog_dev
BOOKSTORE_LOCAL_DB_READS=1
```

The last flag is required for a local `next start` production-build smoke test, not normal development. Restart the server after source/URL changes, migrations or client regeneration. No cloud URL is accepted.

Public catalog pages, related-book sections, series covers and the client collection manifest use the selected read boundary. The original storage key and public IDs remain unchanged. Client-side local validation uses the server-provided public book manifest, not a private ORM model or a second hard-coded fixture list.

Routes deliberately render dynamically so switching source at server restart cannot accidentally serve old fixture-prerendered HTML in database mode. React cache deduplicates only within a request; a singleton initialization promise owns one small read-only pool and survives development HMR. Persistent publishing caches are deferred.

The original loading skeleton is scoped to the catalog listing. A global streaming loading boundary caused unknown dynamic product URLs to return HTTP200 before `notFound()`; moving the unchanged skeleton preserves actual404 behavior for detail routes. Styles and animation components are unchanged.

## Migrations and seed

1. `001_catalog_base`: fourteen normalized catalog tables, ordinary/composite FKs, uniqueness and indexes, timestamps/version on mutable entities.
2. `002_catalog_invariants`: positive ordering/year/version, ISBN format/checksum, primary-series uniqueness, owned-primary-SKU publication and physical SKU identity checks.
3. `003_catalog_identity_checks`: additive nonblank public identities/safe slug checks and published-listing indexes.

Each SQL migration is transactional. Applied migrations are immutable; later hardening is additive. The upgrade test applies001, seeds it, then deploys002/003 and compares identity/DTO parity. This is an intra-batch upgrade test; no earlier production catalog schema exists.

The transactional seed upserts only original demo identities without truncating/deleting other rows. Deterministic UUIDv5 values are entity-qualified; public IDs/slugs remain verbatim. Expected counts:9Works,11Volumes,12Editions,12Products,12SKUs,6categories,2Series. There are no seeded publishers or ISBNs. Omnibus shares the original Volume rows; it does not create duplicate volumes or stock.

## Test safety and CI

`pnpm test:db` requires TEST_DATABASE_URL ending exactly in the isolated test/ci base name. It creates fresh random disposable databases on that same instance. Base databases are never reset/migrated/truncated/dropped by the helper. Cleanup drops only names created by the current run after verifying their database ownership comment; no FORCE is used, and leaked connections fail cleanup.

Coverage includes replay/no-op redeploy, seeded upgrade, seed idempotency, complete fixture/search/public-ID parity, standalone/multi-series/omnibus/anthology, FK/unique/CHECK failures, SKU ownership, draft/non-demo isolation, incomplete metadata, readonly enforcement and real connection failure without fallback.

The existing frontend CI job remains database-independent. A separate PostgreSQL job runs migrations/parity tests on disposable data, then seeds only its ephemeral CI database and runs the same Chromium storefront regressions in database mode. It also runs `pnpm test:source-failure`: owned local servers must return HTTP500 for missing database/invalid source, without fixture content or response credentials. Test servers are stopped by their owning process.

Artifacts retain JUnit database results and per-mode Playwright evidence for7days. No environment files, database files or passwords are included. Actual results belong in the Batch3.1 validation report/PR comment, not inferred from this guide.

## Remaining boundaries

- No staff/customer auth, admin mutations, CMS persistence/publishing, media uploads, inventory tables/adjustments, pricing, orders/payments/shipping, deployment or paid services.
- PREPACKED identity is distinct from single-book Edition; composition/virtual bundles and public box presentation are deferred.
- Read-only sessions and a read-only interface are defense in depth for isolated demo development. Separate operational reader/migration roles, backup/restore and full environment hardening are required before real backend operation.
- Small-catalog snapshot/search preserves exact existing semantics in memory; database pagination/search scaling is future work.
- No new browser-engine/device, screen-reader, load/performance or production-certification claims.
