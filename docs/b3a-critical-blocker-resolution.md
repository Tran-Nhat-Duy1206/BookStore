## 3. Concrete B03 candidates

Candidate labels C1/C2/C3 here mean B03-C1/B03-C2/B03-C3, distinct from the state machine's common transaction rules C1–C9. No candidate is owner-ratified by this investigation.

### C1 — Hooks/ALS/GUC or post-hoc journal only: REJECTED

Preauthorize a case in the private process, set local metadata in before hooks, record mutations afterward, compare final snapshot. This does not authenticate AUTH's claims; before-hook SQL has no demonstrated same physical source connection/transaction, after-hooks are too late, and factor writes bypass those hooks. Email equality/returned ID cannot bind first INSERT; committed A→B→A is not excluded. A source journal is necessary evidence, not positive native verification. Untrusted GUC, callback success/brand, event count or post-hoc signature of latest rows is not B03. NO-GO for this mechanism; adding Migrate authority does not repair its provenance claim.

### C2 — Authenticated transaction-capability ledger with NEW public adapter composition: ALTERNATIVE, UNPROVEN

Concrete proposed shape: S1 (or separately selected S2) commits an exact-case/native-operation source permit before the source transaction; a newly reviewed public custom-adapter wrapper OWNS `Prisma.$transaction`, redeems a secret one-use permit through a fixed narrow function on the RAW tx before any provider write; SQL derives its OWN transaction identity/session user and stores a protected claim. Source triggers bind actual writes/revisions to that protected claim in the SAME transaction. No caller-selected tx ID/GUC/success flag is authority; no claim function writes arbitrary provider data. Plain AUTH cannot mint/read permits and cannot join a different active transaction. Actual SDK completion is still recorded separately by the trusted private integration.

Public construction surfaces exist: custom DBAdapterInstance/createAdapterFactory and transaction implementation; delegating native model CRUD to exported prismaAdapter supplied with public Prisma transaction client is pinned-source-compatible (empty structural client signature, atomic helpers tolerate absent nested `$transaction`). It is NOT inherently monkeypatching. However, explicit upstream documentation promising that particular constructor composition is not established here. A new wrapper must cover ROOT and transaction-derived adapters, direct factor CRUD, all create/update/updateMany/delete/deleteMany/consumeOne/incrementOne and every native helper/autocommit boundary, not just top-level transaction callback. Hook/rollback/cache/output semantics and background work must be retained, no mutable shared current-client setter.

**Unresolved obligations:** opaque permit mint authority/new EXEC grants; first INSERT claims actual generated UID under preauthorized case/permit, not response email; bounded per-source-transaction permit lifecycle before first write; q/journal/root same source TX; exact accepted native grammar; source permits never become ordinary proof. Transactional claim consumption rolls back if the source TX rolls back: it ALONE does not make a permit globally spent after an attempted/unknown operation. A separately durable send/abandon/unknown protocol and no reuse rule is required; do not invent autonomous SQL journaling. Mint-before-source-lock avoids cross-client deadlock only if no AUTH governance/target lock is already held. Complete orchestration/constructor documentation/permit lifecycle is not proven. New wrapper is a TRUSTED persistence/security component and B.2 contract change, not stock adapter support. Reject a generic privileged DML writer/private SDK patch presented as this solution. NOT the preferred next implementation candidate; NO-GO for a claim stock documented configuration already supplies it.

### C3 — Authenticated ONE-OPERATION-PER-LOGIN source lanes: PREFERRED CANDIDATE FOR OWNER REVIEW, NOT RESOLVED B03

**New root L is mandatory and explicit.** Existing fixed-client APIs support making every source statement/transaction of ONE native API call use the same dedicated DB-login/client/pool. No per-request role switch, SDK hook or patch is needed. The source lane authenticates authorized writer origin, NOT that SDK ran or comparison succeeded. A compromised L holder can forge its own allowed transcript; S1's genuine maintained completion and A's exact independent seal remain separate trust requirements. If the owner's threat model requires independent SDK proof against L+S1 compromise, this candidate is NO-GO.

#### Before first User INSERT and first subject binding

1. Existing trusted OFFLINE role hardener/Migrate would, ONLY under future authorization, provision and register a bounded set of source LOGIN profiles for a SINGLE create/password/enable/confirm operation each (identity/email assertion operation separately unresolved). No dynamic role creation by SDK/A/S1 and no credentials now. The role is NEVER recycled for another operation/case, not even after timeout/unknown. Registry identity includes authenticated role identity plus owned DB/realm/incarnation and immutable role lifecycle, not reusable PID or integer OID alone.
2. A independently preauthorizes intended identity/action/Owner case. S1 commits the fixed setup reservation, budgets/TOTP burn when applicable, exact source operation grammar and an immutable authorized lane→case/op mapping BEFORE any source transaction. Selection derives from fixed registered purpose and case, never a caller role name/subject/GUC. Each lane has at most one operation and first-subject claim.
3. The private SDK call uses a separately constructed/frozen client backed by that lane's authenticated LOGIN for its ENTIRE lifetime, including native transaction adapters and selected after-hooks. Ordinary AUTH is not substituted; minimal custody may use one isolated process/client per operation, avoiding cross-instance ambient adapter/ALS borrowing. Supported fixed pool configuration supplies identity; actual connection-role and lifecycle proof is still REQUIRED.
4. Existing/new governance BEFORE-statement locking serializes source writers. A source Guard checks `SESSION_USER` authenticated login against private registry, not definer `CURRENT_USER` or a user-controlled setting. At the FIRST actual trusted-lane User INSERT it validates the approved create grammar/identity contract and atomically binds the actual inserted SDK-generated UID to the previously authorized case/op and initial journal. Insertion, once-only subject attachment and source history commit/rollback together; before-row validation plus after-row claim must preserve real FK timing. Native returned ID, email equality and HTTP success are corroboration only. A duplicate/synthetic signup response with NO authenticated INSERT cannot attach an existing account.

#### Every transaction, history, interleaving and once consumption

- Every source statement derives the SAME fixed lane/op binding from authenticated login; native signup's User+Account(+Session) may be ONE transaction, TOTP confirmation spans several. The operation has an immutable authorization baseline and a protected advancing grammar cursor. Later expected commits advance cursor/q/root; they do not pretend future unknown password hashes/encrypted factor bytes were preapproved or auto-refresh an approval to latest state.
- Proposed protected per-case/subject q increments transactionally under governance with each relevant OLD/NEW source mutation; append opaque table/row identity, fixed mutation/field mask, keyed before/after projections, source-transaction grouping and operation identity. No secret/raw OLD/NEW dump; session lineage separate from provider fingerprint. Journals/spent lane/op/subject tombstones have no provider-delete cascade; delete/reinsert cannot create a fresh baseline or reuse identity. Bounded overflow/missing/continuity failure denies. Source rollback/savepoint rollback leaves no COMMITTED history increment; sequence/transaction-ID gaps are not proof of committed ABA or commit ordering.
- A committed ordinary AUTH critical write to the candidate invalidates q/outcome/seal even when its field mask matches expected SDK changes or it returns bytes to A. AUTH cannot fabricate lane identity without credentials/role authority. Rejected writes roll back their own journal: do NOT claim a durable invalidation event from the same transaction that raises. Both rejection and committed-invalidation can deny safely, with separately bounded failure reporting if needed.
- All six provider models need explicit classification: NEW User/credential Account, first unverified factor, exact verified/enabled flag transition, session create/delete/rotation, rate-limit rows and possible Verification challenge rows. No table-wide expected-write wildcard. Unexpected enabled-account sign-in challenge, unverified-factor overwrite, extra factor, identity/provider rebind, stale target or missing causal prefix denies. Native limiter writes/background pruning are not disabled merely to fit a grammar; a fixed selected call path must prove whether/when request limiting runs and how noncritical delayed work closes safely.
- S1 must finish actual maintained operation/final-cookie/current committed session checks, then under governance close the source operation with a durable no-more-writes barrier, validate final transcript and capture one-use setup-only outcome atomically. Sealing binds that closed transcript/outcome to ONE immutable independent approval only; final activation atomically consumes the linked outcome/approval/case once with its audit. Sealing is not a second ordinary-evidence use, a TTL renewal or permission to re-seal a newer transcript. Delayed old-lane writes after close/expiry/cancel/unknown/activation reject even on still-connected pools. Pool disposal/password revocation alone is NOT a fence; login roles are never reassigned. Do not infer universal SDK quiescence from endpoint await; configured background callbacks/pruning/hook paths need explicit evidence and cannot silently mutate candidate afterward.
- Native failure/partial commit/unknown leaves nonauthorizing case/op with retained burns/history; no new login lane/operation automatically substitutes it. Exact authorized status-only inspection returns confirmed state, not grant/cookie. Normal subsequent proof is freshly prepared through B.2 only after separately approved activation. Whole DB/key/role-history restore can undo history; external OFF/quarantine/incarnation/lineage review remains mandatory.

#### Required boundaries; why this is NOT an authorized generic writer

L is a NEW source-persistence credential/trust surface, not an innocuous label on current AUTH. Case/operation/subject/field-grammar guards must enforce its writes; a lane allowed arbitrary provider DML is REJECTED. It needs exact native model/column/sequence privileges and may require password/factor SELECT for the bound subject; confidentiality blast radius must be disclosed. Existing table-wide provider SELECT does NOT enforce subject isolation. Target-read policy/RLS or an explicitly accepted offline read boundary must be separately designed and tested with the maintained adapter; neither is supplied by hooks or silently approved here. No lane table/column access to private case/journal/approval/generation/admission/clock/key/replay controls, no generic Guard writer, DDL/TRUNCATE/TEMP/trigger disable/membership/SET SESSION AUTHORIZATION/replication bypass, superuser or startup/logging overrides. No grant/schema ownership may let AUTH impersonate L; Guard checks session login, not SET ROLE/current_user. Database authentication/HBA/proxy/peer-mapping policy must also prevent an ordinary AUTH holder from selecting another LOGIN identity without its independently controlled credential: trust authentication or arbitrary user mapping would defeat the attribution claim. This assurance is NOT established by a role name/URL or this source inspection; a later negative connection-authentication test/configuration review is mandatory.

New per-operation credentials, strict profile/URL validation and source guards change approved B.2 persistence/ACL boundaries. The lane proposal is source-supported only at public connection/transaction composition level; NEW SQL registry/cursor/journal/grammar/profile/lifecycle/read-scope semantics remain unproven. It is defensible to INVESTIGATE only if the owner explicitly accepts L and trusted S1 attribution rather than independent SDK proof. Otherwise precise NO-GO, not broaden AUTH/Migrate into a source attestation oracle.
