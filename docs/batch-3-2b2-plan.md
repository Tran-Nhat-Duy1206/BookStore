## 5. State and authority contract

States are explicit and server-owned: anonymous; password-proved/TOTP challenge; enrollment-only; verified admission; recovery-only; expired/revoked/suspended/disabled. A provider identity/session or `twoFactorEnabled`/`verified` boolean does not establish application MFA proof.

- Ordinary admission requires separately approved active staff, active governance, valid same-user provider session, fresh complete password+actual TOTP login, current authorization/permission version, no relevant pending/blocked transition, unexpired original epoch and no revocation tombstone.
- Enrollment-only state never grants normal admission. Keep enrollment/confirmation HTTP routes unmounted in B.2; study their SDK behavior privately and exercise denial tests. Real initial/replacement enrollment and its server-approved lifecycle remain B.3. If the owner wants even purpose-only enrollment transport earlier, approve that additional manifest/secret-display capability explicitly. Successful provider enrollment never activates a pending principal, grants roles or bootstraps an Owner.
- Recovery is represented and denied normal permissions; no backup-code/recovery/last-Owner activation endpoint in B.2. Reject the hidden provider backup route too. Real recovery stays B.3 and requires independent proof/operator/key decisions.
- Step-up requires already valid normal admission, actual TOTP and the same user/session/version/epoch; it updates recent-MFA evidence only. It cannot create admission from an old/first-factor/recovery/revoked session, refresh inactivity after expiry or reset absolute age.
- No remember/trusted-device bypass, public signup, account linking, social/passwordless/email-OTP, public reset, factor disable, identity deletion/email/status/role update or impersonation endpoint.

### Proposed positive-MFA authority — blocking security decision

**B.2a boundary:** the following durable/signing/finalizer designs are preserved proposals for B.2b. B.2a creates no positive-grant authority. Its proposed private WeakSet-branded observation records safe IDs, expected authorization version before/after, factor-ID lineage and start/end time interval for the actual SDK operation. It carries no secret/token/OTP, is not serializable authority and cannot survive process loss as proof. A pure binding comparison may report binding validity but must always return `admissionAllowed: false`; valid binding is NOT MFA proof attestation.

Add private short-lived verification-attempt/evidence state. BEFORE verification, bind a one-use purpose challenge to the SDK-validated primary operation, user, EXPECTED authorization and factor/credential epochs, original login lineage, browser/CSRF context and server operation ID. The receipt then binds that exact challenge to the actual resulting provider session and observed MFA time. Never adopt a newer authorization version merely because it exists after verification. No raw challenge/token/OTP value is copied into audit or general DTOs; no client can choose authority fields.

**Recommended authority model to prove first:** a fixed authenticated internal verification receipt, signed/MACed only by the private SDK-success path and verifiable by the narrow SQL finalizer under the nonlogin owner. Fields include issuer/audience/key-id/purpose/jti, challenge digest, user, final session, expected versions/epochs, observed times, original deadline and keyed replay fingerprint. Use reviewed maintained cryptographic primitives, exact canonical encoding and constant-time verification, not homemade TOTP/password logic. Staff receives EXECUTE on consume/step-up/touch/challenge functions, never arbitrary admission/proof INSERT. Auth/worker cannot issue receipts or read the verifier key. Database verifier availability/extension and private key custody/rotation are feasibility and owner-approval gates; B.1 does not provide them.

**Alternative requiring explicit topology approval:** a separate purpose-limited attestor DB credential that can only register bound one-use evidence, with no identity CRUD/role/governance authority. It must not become an unrestricted fourth writer or let staff/auth call a generic proof-mint function. Add an exact purpose validator, not a relaxed username/URL guard. Compare this credential authority with the signed-receipt option in B.2a and ratify ONE before implementing a writer; no silent fallback to broad DML or migration credentials.

In either model, the server-only verifier is a trusted positive-grant authority; SQL cannot magically prove that an application performed TOTP. Keeping signer/verifier and staff credentials in one process does not protect against complete process compromise. No public arbitrary-claims signing/proof API and no worker promotion. Any stronger process-isolation requirement is a separate owner decision.

Exact pinned SDK hooks/result/commit guarantees must be proved in B.2a. `transaction:true` config does not mean the whole endpoint is one transaction. A session-created event, generic after-hook, HTTP200, cookie presence, enrolled flag, old JSON token or TypeScript brand is not sufficient. Resolve the final session through the effective validated response cookie changes and authoritative SDK lookup; if this cannot be made reliable without refreshing/mutating bindings, STOP and review the integration contract.

### Required completion ordering

1. Reconcile earlier relevant events first, validate eligibility/real primary authentication and prepare a one-use challenge against the CURRENT expected version/epochs. Commit/release staff/governance locks BEFORE calling the provider. Reserve atomic shared abuse budgets before expensive verification.
2. Run the maintained TOTP operation and await confirmed provider completion. Capture observed verification privately and resolve the actual final session from validated effective cookies. Crash before durable receipt means no proof/no admission and fresh verification, never inferred success.
3. If verification caused an invalidating enrollment/factor/credential event, DO NOT admit and DO NOT rebase the old proof to a newer version. Finish bounded deny-only reconciliation, discard stale proof and establish a NEW current-version challenge plus fresh TOTP (fresh password too if credential/primary binding changed). Blocked/saturated/incomplete processing yields503/denial. Normal B.2 positive tests use preapproved, pre-enrolled synthetic principals; real enrollment activation remains B.3.
4. For a stable normal-login/step-up operation, attest ONLY the original prepared challenge/version/epochs and actual final session. Re-read required live state; any intervening version/revocation/epoch change invalidates the receipt. No infinite request drain or latest-version adoption.
5. In ONE READ COMMITTED staff transaction: acquire governance first; capture post-wait clock; verify receipt authenticity/bindings, same-user/session ownership/expiry, active principal/governance, original version/epoch, purpose and challenge/proof TTL, no relevant pending events and durable revocation controls. CAS consume challenge+jti+cross-purpose OTP replay reservation, write only the permitted admission/step-up change and append success audit atomically. Audit failure rolls back all local grant/consumption state. Provider state already committed remains non-privileged on failure.
6. Forward only allowlisted final cookies and minimal state. A bound duplicate may only return the identical already-finalized result after live revalidation, not grant again. Ambiguous COMMIT/cookie delivery is not reported as certain rollback; require fresh login if safe rebinding cannot be proved. Never persist/replay a raw saved bearer response for idempotency.

### Pinned SDK caveats verified by source, not new test execution

- The SDK sign-in helper consumes its verification challenge once before creating a session. The active-session branch used for step-up/enrollment has no equivalent consume/attempt enforcement; its attempt helpers are no-ops, and TOTP account-lockout calls are conditional on sign-in. Application-owned one-use purpose challenges and shared budgets are mandatory for step-up, not an assumed SDK guarantee.
- Maintained OTP verification accepts the configured time window (default current±1step,30seconds each) and returns only a boolean. It does not persist cross-challenge replay counters. Propose a maintained-crypto keyed accepted-code fingerprint scoped globally to user+factor epoch across ALL MFA purposes, never raw OTP or an unkeyed guessable digest. CAS reserve it with challenge/proof consumption and admission audit; two concurrent uses have one winner. Retain for the full conservative acceptance horizon plus bounded trusted-clock skew (default reach can span about90seconds, not just30); prove the exact bound and collision-denial behavior. Key rotation must not reset a live replay window. If clock/replay persistence cannot be proved, STOP rather than claim replay protection.
- Enrollment confirmation can update User.twoFactorEnabled, create/set a new session cookie, delete the old session, then mark TwoFactor.verified. Its active-session success helper can still return the old JSON token. Therefore JSON token is not a reliable final-session identity and enrollment cannot reuse old version-bound evidence after reconciliation. The effective response cookies plus authoritative SDK resolution and a NEW challenge are required.
- The experimental admission harness has broader write/upsert/touch authority than production B.1. Do not import/promote it as the B.2 writer. The new least-privilege proof protocol must be independently reviewed.

## 6. Session control, revocation and activity

The original authentication epoch must survive identifier rotation. A step-up, touch, resolver lookup or provider refresh cannot move it. Recommend durable authorization lineage/control metadata bound to provider sessions, not an alternative authentication/session engine.

B.1 self-revocation changes admission mode but does not increment the user's global version, and reconciliation can delete admission rows. Therefore a B.2 writer needs a durable revocation/epoch tombstone independent of that removable row. A stale cookie/new proof must not recreate admission for a locally revoked old session. Normal re-login requires fresh password+TOTP and a new approved login epoch; revoked lineage cannot silently rotate into a fresh absolute window.

Expiry is checked before any touch, inside the same governance protocol. Candidate8h/30m/5m remain unapproved operational settings. Define qualifying activity conservatively: protected explicit foreground operations may touch; session status, polling, prefetch/Flight and assets do not. RSC reads are read-only initially; do not write cookies or extend idle just because a page was prefetched. The exact activity definition requires owner agreement before real use.

Sign-out is deny-only: clear owned cookies regardless of persistence outage, attempt durable local revocation/audit and provider session revocation without cross-client held locks. Preserve retryable deny evidence; no all-device revocation guarantee if persistence is unreachable. First-factor/enrollment/recovery sessions may sign out without ordinary admin admission, but still require the transport's origin/CSRF rules.

## 8. PostgreSQL abuse controls and client-IP policy

Pinned1.7.18 source DOES use guarded atomic mutation: the database limiter calls conditional `incrementOne` with `count<max` and a guarded window reset; the Prisma adapter retains those predicates plus row ID and uses an atomic increment under a transaction. Do not misdescribe it as naive read/overwrite. Still prove actual PostgreSQL multiworker/window/retry behavior and compound account/challenge budgets; `storage:'database'` alone does not establish that broader policy. Retain native protections and add only the reviewed atomic shared gate/reservations needed for the application policy.

Propose separate protected abuse/attempt reservation state: fixed policy version, trusted normalized keyed account/IP/challenge digests, server clock, canonical sorted multi-key locks and bounded leases. Reserve before expensive password/TOTP work so parallel attempts cannot all pass a read-then-increment check. Complete reservations idempotently on result; crashes/unknown results remain conservatively charged until a bounded reviewed expiry. No ordinary role can reset/raise limits using client values, and no in-memory fallback on store outage.500/503 or429 responses do not leak account existence.

Starting thresholds remain recommendations: password5failed/account/15m plus20attempts/trusted IP/15m; MFA10failures/account/15m across challenges/IPs, plus the native3requests/10s two-factor path/IP rule. The SDK sign-in challenge's separate failed-attempt helper is5; neither mechanism substitutes for global per-account/purpose replay and step-up controls. Pending reservations count toward the failed-attempt budget until resolved; password success alone cannot reset MFA/consecutive failures. Define attempt-vs-failure accounting, successful-full-MFA reset semantics, progressive cooldown, fixed windows and lockout-DoS behavior before coding final transport. Never copy the spike's high fixture budgets or synthetic client-IP header.

A Next Web Request does not automatically expose authenticated socket provenance. Pinned core defaults to `x-forwarded-for`; its `trustedProxies` option interprets header chains but does not authenticate the connecting peer. Default policy: strip all supplied Forwarded/X-Forwarded/X-Real-IP/x-spike-client-ip variants and configure `ipAddressHeaders: []` until a reviewed ingress exists. Do NOT set `disableIpTracking`, because the pinned limiter bypasses enforcement when tracking is disabled. Empty trusted-IP headers yield dev/test loopback or a production shared no-trusted-IP bucket; retain the application account/common-IP gate rather than bypassing limits. For a strictly loopback-only direct development listener, use a conservative common loopback/unknown-IP bucket if peer identity cannot be proved; do not pretend it separates remote clients. A reviewed ingress may derive peer IP, strip all supplied variants, overwrite metadata and authenticate the sole trusted hop/backend channel. Until that chain is proven, deny flows needing stronger attribution or retain the conservative common bucket. No production proxy trust is implied.
